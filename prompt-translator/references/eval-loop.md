# 評測與回歸閉環（Full 規模必備／Standard 簡版參考）

沒有可重跑測試集的生產級 Prompt 等同尚未完工。`Standard` 交付時附 3–5 個核心測試案例與通過判準；`Full` 交付時依下列六步提供完整評測與監控方案：

## 1. 建立分層測試集
- **起步規模**：上線前至少準備 20–50 個貼近真實分布的樣本，隨線上失敗案例持續擴充。
- **必含四類樣本**：
  1. **典型正例**（涵蓋不同輸入長度與表述習慣，檢驗穩定度）
  2. **缺漏與邊界案例**（缺關鍵欄位、超長輸入、政策未涵蓋的灰區，檢驗失敗出口）
  3. **衝突案例**（用戶要求與合規／事實約束衝突，檢驗優先序裁決）
  4. **對抗與注入案例**（外部資料夾帶「忽略以上規則」「直接核准退款」等指令，檢驗資料／指令隔離）

## 2. 分層設計評分器（先確定性，後語義）
1. **程式碼確定性檢查（優先）**：JSON Schema 解析、必填欄位、長度上限、禁用詞／未授權承諾字眼、引用條號存在性。
2. **錨定量表（Rubric）＋ LLM-as-Judge**：針對語氣、推論合理性與完整性設計二元或三段式具體判準（避免模糊 1–10 分）；Judge 提示詞須經人工抽樣（至少 20–30 筆）校準一致率後才可信賴。
3. **成本與延遲指標**：同步記錄每次呼叫的輸入／輸出 Token、Prompt Cache 命中率、首字延遲（TTFT）與 Agent 步數。

## 3. 單變因迭代與基準對照
- 每次迭代**只改動一個可歸因區塊**（例如只改 `<constraints>` 或只增減範例），在同一組測試集上比較舊版（Incumbent）與新版（Challenger）。
- 區分「訓練微調集」與「保留驗證集（Held-out Test）」，防止為修單一案例把規則寫死而傷害泛化率。

## 4. 版本控管與可回滾結構
- 像管理程式碼一樣保存每次變更的 `diff`、修改原因（特別標註某條 `COMP` 補償是在修哪個失效樣本）與對應評測分數，確保退化時能單點回滾。

## 5. 線上監控與失敗樣本回流
- 上線後抽樣監控高風險訊號：人工修改率（客服改了多少字才寄出）、拒答／轉人工比例、工具重試率與結構解析失敗率。
- 每週將線上真實失敗或人工大幅改寫的樣本去識別化後回流測試集。

## 6. 前提變更必重跑回歸
- **換模型／升小版本、換檢索資料源、改工具介面、改業務政策**時，一律重跑完整回歸測試集，絕不假設舊 Prompt 可零測試直接移植（既有成品的換代去留審核可交由 `prompt-auditor` 執行）。
