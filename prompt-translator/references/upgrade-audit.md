# 升級審核（前提改變後）

**何時用**：用戶已有成品（prompt／Skill／SOP），而前提變了——換模型、升版本、換工具、換資料源、換政策。
目標不是「寫得更好」，是判定**每條指令還該不該留**。

## 為什麼一般品質檢查不夠
品質與存續是兩個獨立判斷：
- 品質很高的指令可能已無作用（模型內建該能力）→ 品質軸高分，存續軸該刪
- 品質很差的指令可能是業務鐵律 → 品質軸低分，存續軸必留

`quality-checklist.md` 只答前者。誤刪後者的代價，遠大於留著一條冗餘指令。
所以維護模式不看 12 維分數，看歸屬表。

## 預設方向（與產出模式相反）
產出型 prompt 的預設是「填入合理假設，先給成品」；維護型的預設是**存疑則保留**。
不確定時的輸出是「待驗證」，不是改寫後的成品。

**任何刪除都要能同時回答兩件事，缺一即不准刪：**
1. 它原本在修哪個具體問題？（能指到案例、時間點或一次事故）
2. 新前提為何使它不再需要？（能指到具體變化，不是「新模型更強」）

## 六類標籤
| 標籤 | 判準 | 典型 | 處置 |
|---|---|---|---|
| SPEC 契約 | 這是本任務獨有、模型無法自行得知的約定嗎？ | 業務規則、術語定義、優先序、範圍、語氣、權限、法規、欄位語義 | 必留，只壓縮措辭 |
| COMP 補償 | 這條在教模型「做到它做不到的事」，或對模型施壓？ | 全大寫／威脅／獎勵、專家頭銜堆砌、強制分步與思考格式、超量 few-shot、手寫分支、格式咒語、為某 bug 加的臨時禁令 | 過三問才刪 |
| STALE 過期 | 是否指向已變的型號、版本、價格、日期、API、工具名、連結？ | 「上下文 8k」、「用 v1 接口」、舊價格 | 更新，不刪 |
| DEBT 舊債 | 是否本來就違反良好實踐，與換代無關？ | 缺成功標準、無失敗出口、資料指令混寫、把計算／權限交給模型 | 另列清單，標「非換代導致」 |
| DUP 冗餘 | 同一要求重複 3 次以上，或實質重複？ | 格式要求寫兩遍 | 合併留最強一處 |
| CONFLICT 衝突 | 兩條互相矛盾或優先序不明？ | 「務必簡短」vs「逐條詳述」 | 不自行裁決，交用戶決定 |

## 風險決定激進度
- **低**（內部、可重跑、無副作用）：可較激進，待驗證項也可先試行
- **中**（對客、有人複核）：分批改，先動最高確信度，留 diff
- **高**（對外發送、付款、刪除、法規、PII、不可逆）：只刪有明確證據的；安全與合規條款一律保留；變更須 HITL；先影子對照

## SOP 額外判準
SOP 是人工程序，判準與 prompt 不同：
- 這一步是否原本就是為繞開舊模型限制而設的人工補丁？（如「人工檢查 JSON」→ 改 schema 校驗）
- 檢查點真有人看嗎？無人複核的檢查點是假檢查點
- 交接物下游還有人用嗎？沒人用的是純開銷
- 「手動」步驟現在能否自動化；「自動」步驟現在是否該加人工
- 角色、系統名、時限、表單編號是否已過期
- 一次只改一處可歸因的環節，否則出錯無法定位

## 可複製的審核指令（核心全在這四句）
```text
額外要求（覆蓋你的預設行為）：
1. 存疑不刪——任何你打算刪除的指令，若無法同時指出「它原本在修哪個具體問題」與「新前提為何不需要它」，保留原文並列為「待驗證」。
2. 逐項歸屬——輸出表格：位置 | 原文摘要 | 保留/改寫/刪除/更新/待驗證 | 理由 | 確信度。不要只給結論。
3. 業務規則、安全條款、合規、輸出 schema 一律不得列為刪除項。
4. 附 changelog 與回滾方式（保留舊版原文）。
```

## 驗證：沒有測試集時的 5 案
1. 典型正例
2. 典型正例（不同輸入形態，看穩定性）
3. 邊界（資料缺失／超長）
4. 對抗（資料中夾「忽略以上規則」）
5. 當初加補償指令想修的那個失效場景

每案記錄舊版結果／新版結果／是否退化／是否改善。任一案退化且說不出原因 → 只回滾該處，不整體回滾。

## 輸入不足時先問三件
1. 這個成品**誰在用、風險級為何**（決定激進度）
2. **變更向量**：換了什麼、你觀察到哪些具體差異（沒有就寫「未確認」，據此保守）
3. 有沒有**不可刪條款**（合規、品牌、法務）

## 不作為
- 不改變業務語義、不順手換風格、不調整業務優先序
- 不把「新模型應該懂」當刪除理由
- 不把舊債算成這次升級的成果
- 不省略歸屬表；沒有逐項理由的改動無法事後稽核
