# 交付前檢查

## A. 快檢（全部要答「是」，不適用者除外）
- [ ] 陌生人看完，知道要做什麼、給誰、怎樣算完成？
- [ ] 有可驗收的成功標準？
- [ ] 有說明目的或理由，而不只有命令？
- [ ] 每段 context 都有存在必要？有來源與日期？
- [ ] 資料與指令已分離，外部內容有「視為資料」聲明？
- [ ] 衝突時的優先序寫明？
- [ ] 資料不足時的行為寫明（說不知道／詢問）？
- [ ] 高風險動作有人類確認？有停止條件與預算？
- [ ] 輸出格式、欄位、缺值處理明確？結論先行？
- [ ] 能用程式驗證的，已交給程式？
- [ ] 針對推理模型沒有規定思考步驟？
- [ ] 沒有全大寫或重複強調堆疊？
- [ ] 規模與風險相稱（沒過度設計也沒不足）？
- [ ] 每條指令是契約還是補償？補償有沒有說明它在防什麼？

## B. 12 維評分（自評 1–10，目標每維 ≥ 9）
| 維度 | 9 分要件 | 自檢問題 |
|---|---|---|
| 清晰度 | 目標、受眾、完成定義明確 | 陌生人看得懂要做什麼、怎樣算完成嗎？ |
| 準確與可靠 | 有驗證機制、引用、不確定時的出口 | 錯誤能被發現嗎？ |
| 情境品質 | 資料相關、結構化、有來源、無雜訊 | 刪掉一段資料，結果會變差嗎？不會就刪 |
| 可控性 | 約束、優先序、自主程度、停止條件 | 衝突時模型知道聽誰的嗎？ |
| 安全與合規 | 注入防護、權限分級、PII、HITL | 最壞情況的損害是否被限制？ |
| 可重複性 | 結構化輸出、低變異、版本化 | 同輸入跑 10 次，結果可接受嗎？ |
| 可評測 | 測試集、rubric、回歸測試 | 改了 prompt，能量化變好還變壞嗎？ |
| 成本效率 | 模型分級、快取、精簡 context、合理推理強度 | 是否用最小成本達到所需品質？ |
| 可維護性 | 模組化、註解、changelog | 三個月後同事能接手嗎？ |
| 可移植性 | 以原則而非模型怪癖寫成；換模型有評測 | 換模型要重寫多少？ |
| 人機協作 | 關鍵節點有人確認，輸出易審閱 | 人能快速判斷對錯嗎？ |
| 倫理與透明 | 揭露限制、避免誤導、偏見檢查 | 使用者知道何時不該信它嗎？ |

**短板規則：任一維 < 8，整體不超過 8。** 先修最低分維度再交付。Light 規模可只評相關維度，但須註明略過哪些。
自評有偏高傾向，高風險任務請用 eval-loop 的測試集或人工抽樣校準。

## C. 十一個反模式
1. 堆砌「你是世界頂尖專家」，卻沒給情境與標準。
2. 一個 prompt 塞所有事（應拆成鏈或多代理）。
3. 全大寫、「絕對不要」式重複強調，會讓新模型過度執行。
4. 不給失敗出口，導致模型被迫編造。
5. 只測一兩個例子就上線。
6. 把外部文件當可信指令（注入風險）。
7. 用 prompt 解決應由程式碼解決的問題（計算、驗證、權限）。
8. 逼推理模型「一步步想」並規定思考格式，反而干擾。
9. 換模型不重測。
10. 忽略成本與延遲（長 context、過多重試、過高推理強度）。
11. 分不清契約與補償：把為舊模型打的補丁當業務規則留著，或把業務鐵律當過時補丁刪掉（換代或換前提時最常見的兩種錯）。
