# Prompt Auditor

## 核心準則
- **品質軸與存續軸分離**：寫得極佳的指令可能已因模型內建該能力而成為冗餘（存續軸可刪）；寫得笨拙的句子可能是不可觸碰的業務鐵律（存續軸必留，僅能壓縮措辭）。
- **預設保守（存疑則保留）**：審核既有成品與從零產出相反——來歷不明的限制一律先保留並標為「待驗證」，禁止憑「新模型應該懂」或「看起來多餘」直接刪除。
- **先歸屬、後動刀**：逐條標記六類標籤（`SPEC`／`COMP`／`STALE`／`DEBT`／`DUP`／`CONFLICT`），沒有逐項歸屬理由的改動無法事後稽核與單點回滾。

## 工作流程

### Step 1｜確認審核情境與風險激進度

**1. 審核路徑**
- **路徑 A｜品質診斷與重構（前提未變）**：既有成品效果不穩、太肥、全大寫堆疊或快取失效。重點清理 `DEBT`（結構舊債）、`DUP`（冗餘）與明顯干擾模型的 `COMP`（過度施壓／強迫推理步驟），**完整保留所有 `SPEC` 業務語義**。
- **路徑 B｜換代／前提變更存續審核（前提已變）**：換模型、升版本、換工具、換資料源或換政策。重點判定每條 `COMP` 是否仍必要、更新 `STALE` 過期資訊，並將 `DEBT` 獨立列出（不冒充為換代成果）。
- 若審核對象為含人工環節的 **SOP**，加讀 [`references/audit-rubric.md`](references/audit-rubric.md) 第 3 節。

**2. 風險決定動刀激進度**
- **環境可查就先查**：若目標檔案位於工作區，先檢查鄰近程式碼、`git log`、Schema 與既有測試案例，找出舊規則當初修補的事故脈絡。
- **缺上下文時採中高風險保守預設（免攔截追問即可出報告）**：若用戶未說明變更向量、風險等級或不可刪紅線，標註「變更向量未確認 → 採保守預設（存疑不刪）」，首輪直接產出完整歸屬診斷；唯有用戶忘了貼出待審核成品時才先索取原文。
  - **低風險**（內部自用、可重跑、無外部副作用）：可一併重構結構並將待驗證項提供精簡試行版。
  - **中風險**（對客草稿、有人工複核）：分開「高確信必改項」與「待驗證項」，保留清楚前後差異。
  - **高風險**（全自動對外、付款／退款、刪除、法規、PII、不可逆）：只刪具備雙重明確證據的項目；安全、合規與輸出 Schema 一律保留；建議影子對照（Shadow Eval）後再切換。

### Step 2｜逐條歸屬分類（六類標籤）

完整判準、邊界案例與 11 項結構反模式見 [`references/audit-rubric.md`](references/audit-rubric.md)。審核時必讀並逐段歸類：

| 標籤 | 核心判準 | 標準處置 |
|---|---|---|
| **SPEC 契約** | 本業務獨有、模型不可能自行得知的約定（業務規則、術語、權限、法規、優先序、語氣紅線、欄位語義） | **必留**；僅在不改語義下收斂措辭 |
| **COMP 補償** | 為彌補舊模型弱點或對模型施壓的補丁（全大寫咆哮、專家頭銜、硬性分步 CoT、超量範例、臨時 bug 禁令） | **通過「刪除雙問」才准刪**；來歷不明標 `待驗證` |
| **STALE 過期** | 指向已變更的型號、上下文長度、API 版本、工具名稱、價格或日期 | **就地更新並標註新日期**，不直接刪除整個區塊 |
| **DEBT 舊債** | 與換代無關、原本就違反工程實踐（缺驗收標準、缺失敗出口、未防注入、動態資料破快取、叫模型算帳） | **修補結構**；路徑 B 須標明「既有舊債修補」 |
| **DUP 冗餘** | 同一要求散落多處重複叮嚀（非刻意設計的尾端目標重申） | **合併收斂至單一權威區塊（Co-location）** |
| **CONFLICT 衝突** | 兩條規則互相矛盾且無優先序（如「務必 50 字內」vs「逐條詳列完整法條原文」） | **禁止私自裁決**；並列衝突處交由用戶拍板 |

**刪除 `COMP` 的雙重舉證鐵律（缺一即保留並標 `待驗證`）：**
1. 能明確指出它**原本在修哪個具體失效問題**？（例如舊非推理模型跳步算錯，而非可能是品牌規範的「句尾不加 emoji」）
2. 能具體指出**新前提為何使它不再需要**？（例如「已改由程式端 JSON Schema 硬校驗」或「目標已換成原生推理模型，手寫 CoT 反而干擾」，絕不用「新模型變強了」當空泛理由）

### Step 3｜安全重構與自檢
1. **零業務語義漂移**：核對原稿每一條 `SPEC`、安全合規條款與對下游承諾的輸出欄位，確保改寫版無遺漏、無偷換優先序、無擅自換文風。
2. **補齊關鍵結構防線（針對 `DEBT`）**：
   - 補上可驗收完成定義、明確失敗出口與外部輸入防注入隔離。
   - 調整區塊順序為「**靜態規則與範例前綴 → 動態 `<context>{{資料}}</context>` 與用戶輸入後綴**」，修復 Prompt Caching 失效問題。
   - 把算術、格式檢查與權限閘門移交程式或 Structured Outputs，並在交付區註明需程式碼配合的項目。
3. **設計回歸驗證案**：針對被刪除／改寫的 `COMP` 與修補的 `DEBT`，依 [`references/audit-rubric.md`](references/audit-rubric.md) 第 4 節擬定對照測試案（含當初加補丁想防的那個失效場景）。

### Step 4｜交付格式

維持精練、可稽核、可直接回滾：

```markdown
## 審核結論
- 審核路徑與風險級別（含變更向量假設）
- 核心診斷結論（最關鍵的 1–3 個病灶，或「全屬業務契約建議維持原版」）

## 逐項診斷與歸屬表
| 位置 | 原文摘要 | 標籤 | 處置（保留／改寫／刪除／更新／待驗證） | 理由與確信度 |
|---|---|---|---|---|

## 改寫／升級後成品
（可直接替換使用的完整 code block；若重複呼叫已拆開靜態前綴與動態後綴則標示清楚；若判定無須改動則明寫「維持原版不動」）

## 前後關鍵差異與待確認項
- **主要變更摘要**（刪／改／補各解決了什麼問題，以及回滾切點）
- **待驗證與衝突裁決**（針對 `待驗證` 與 `CONFLICT` 項目，說明需要什麼證據或用戶決定）
- **建議對照測試**（上線前必跑的新舊版對比案例）
```

## 範例

### 範例｜換模型後的存續審核（含「假補償、真契約」陷阱防護）
**用戶**：「我們從舊款小模型換成最新推理模型了，幫我審核這份對客通知 prompt 哪些可以刪：
`你是世界第一的客服大師！！！絕對不要算錯天數！請一步一步寫出你的思考過程再回答。回覆限 120 字內，只引用退貨政策 v3，絕對不要承諾賠償，句尾不要加 emoji。客戶來信：{mail}`」

**判斷**：路徑 B（換為推理模型），對客溝通屬中風險 → 讀 [`references/audit-rubric.md`](references/audit-rubric.md) 逐條歸屬：

| 位置 | 原文摘要 | 標籤 | 處置 | 理由與確信度 |
|---|---|---|---|---|
| 開頭 | `你是世界第一的客服大師！！！` | `COMP` | **刪除** | 空泛專家頭銜與驚嘆號施壓，無業務資訊量（高） |
| 第 1 句 | `絕對不要算錯天數！` | `DEBT` / `COMP` | **改寫移交程式** | 日期天數應由外部程式算好傳入變數，靠咆哮無法保證算術正確（高） |
| 第 2 句 | `請一步一步寫出你的思考過程再回答` | `COMP` | **刪除** | 舊小模型 CoT 拐杖；新目標為原生推理模型，強制輸出思考過程既干擾內部推理又把草稿暴露給客戶（高） |
| 第 3 句 | `回覆限 120 字內，只引用退貨政策 v3` | `SPEC` | **保留** | 版面與政策依據契約，不因換模型改變（高） |
| 第 3 句 | `絕對不要承諾賠償` | `SPEC` + `COMP` | **改寫保留** | 不承諾賠償屬法務鐵律（必留），但去掉「絕對不要」改為正向明確邊界＋法務理由（高） |
| 第 3 句 | `句尾不要加 emoji` | `COMP` 或 `SPEC` | **保留並列待驗證** | 無歷史脈絡：可能是修舊模型愛亂加表情的補丁，也可能是品牌正式語氣規範；存疑保留（中） |
| 結尾 | `客戶來信：{mail}`（無標籤隔離、無失敗出口） | `DEBT` | **增補結構** | 既有舊債：補上 `<customer_mail>` 防注入聲明、缺資訊出口，並將動態輸入置於靜態規則後（高） |
